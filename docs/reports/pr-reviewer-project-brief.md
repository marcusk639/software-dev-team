# PR reviewer: project brief for software-dev-team

> **Snapshot.** This brief describes `main` at commit `9fdc3fb` (2026-10-26), with `@anthropic-ai/claude-agent-sdk` 0.3.283. It is the understanding phase of the repo-aware PR reviewer rollout; the design that follows from it is `docs/specs/pr-reviewer-design.md`. Check claims about current behaviour against the source.

## 1. What the project is and who uses it

`software-dev-team` is a CLI (`pnpm start "<task>"`) that runs an "Engineering Manager" agent on the Claude Agent SDK. The manager plans and delegates to eleven specialist subagents (`src/team.ts:32-44`), and every tool call passes a safety hook before it runs. It works on real files in a target checkout (`--cwd`), often unattended (`--yes`).

The user is Marcus. He points it at his own repos. Other projects can customize its prompts through `<cwd>/.claude/dev-team/` (`src/prompts.ts:63-66`), so the role names and prompt section names are a public interface.

What it promises, in order of how much a regression costs:

1. **Safety.** It blocks destructive commands, secret reads, writes outside `--cwd` and writes to `.git/`, `.claude/`, `.mcp.json` and `CLAUDE.md`. This holds in every permission mode and inside subagents (`src/permissions.ts:367-373`). This promise is the reason the project exists. An unattended run on a real repo depends on it.
2. **Role boundaries.** The manager may only read, plan and delegate (`src/tools.ts:45-53`). It may delegate only to team roles or the target's own agents, with no model override on pinned roles and no isolation (`src/permissions.ts:187-203`).
3. **Honest evidence.** The ledger records what each role actually ran (`src/ledger.ts`). The manager checks specialists' claims against it (`src/orchestrator/prompt.md:32`), and `--strict` turns anything that needs checking into exit 3 (`src/outcome.ts:23-50`).
4. **Customizable prompts** that fail fast on typos (`src/prompts.ts`, `src/team.ts:57-78`).
5. **CLI behaviour**, including `--allow` rule syntax, `--resume`, `--max-budget`, exit codes 0/1/2/3 and the usage text (`src/cli.ts`, `src/index.ts`).

## 5. Conventions as practised

- **Fail closed.** Every throw in the hook denies (`src/permissions.ts:374-440`), and an unevaluable policy denies (`safeDenyReason`).
- **Comments say why, and cite live evidence and the SDK version.** Facts assumed but not verified against 0.3.283 are marked "unverified" (PR #5). A new SDK assumption without either is a departure.
- **Every bypass fixed is pinned by an exact-input test that asserts the reason.** Review rounds get their own files (`permissions-round2.test.ts`, `-round3`, `-bypasses`, `-messages`, `-message-false-positives`).
- **Errors say what to do.** Deny reasons and CLI errors name the fix ("Delegate again without a model override", `--cwd` errors name the errno).
- **Typed lists of tools** use `as const satisfies readonly ToolName[]`. `exactOptionalPropertyTypes` means optionals are written `?: T | undefined`.
- **Prompts** are XML-sectioned, end with a self-check (`<verification>`), and are never reformatted (L14).
- **No runtime dependencies** beyond the SDK. Tests use `node:test` through tsx with real temp directories (`mkdtempSync`) and fake credential values.
- **Commits** are conventional (`feat|fix|refactor|docs|chore`, optional scope such as `(cli)` or `(prompts)`), with a body that explains why and a `Claude-Session:` trailer. **PRs land as merge commits** (`9fdc3fb`, `9fe2d03`), so commit subjects reach `main` and the PR title does not.
- **No file-size rule.** `src/permissions/shell.ts` is 681 lines.

Where the docs and the code disagree:

- PR #1 noted that role names in the orchestrator prose are hard-coded and unchecked. That is still true (L1).
- `docs/reports/*.md` describe `09f238e`. They are labelled as snapshots, which is intended.
- The PR #5 body asks for a squash merge, and the merge was a merge commit (C11). This is history, not a code problem.

## 6. Intentional, and not to be flagged

- Commit and PR messages that name a blocked command or protected file are denied. This is the accepted false positive (`74ef64e`, `src/permissions-message-false-positives.test.ts:1-7`), and the workaround is `git commit -F`.
- Glob patterns are not screened for secret names, because Glob lists names only (`src/permissions.ts:216`). Grep inside `--cwd` with no glob is allowed, and secret files must be gitignored (PR #4).
- The Bash layer is documented as best-effort pattern matching, not a sandbox (`src/agents/team/prompt.md:19`; PR #5 "Known gaps"). A gap in a category the repo already lists as known is not new, unless the PR claims to close that category or widens it.
- `DEFAULT_ALLOWED_TOOLS` is empty on purpose (`src/allowlist.ts:42`).
- `settingSources: ["project"]` loads the target repo's hooks and MCP servers. This is a documented trust boundary (`src/orchestrator/index.ts:188-194`).
- The undocumented `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS` env var is used knowingly, and the delegation guard enforces the same thing (`src/orchestrator/index.ts:196-201`).
- `dir/*` read rules outside the project are rejected rather than granted one level (PR #5).
- Judge roles (qa-tester, code-reviewer, architect) run on opus, which costs more on purpose (`e3ef368`, `src/agents/qa-tester/index.ts`).
- Fake credentials in tests, such as `sk-ant-test-0123456789abcdef` (`src/permissions.test.ts:25`) and `ghp_0123456789ab` (`:713`), and `.env` files written into temp projects are fixtures.
- PR #3 is a byte-identical re-landing of PR #2.

## 7. Sensitive material, and who can see what

- **No secrets or PII.** The repo holds no credentials. `.env` is gitignored, and there is no PII domain.
- **The sensitive content is the safety policy's weak spots.** A concrete input that gets past the hook is an exploit against anyone running the team unattended on content they don't control: target repo files, fetched web pages and specialist reports all reach the agents. Committed knowledge must describe classes and counterpart paths only, never bypass inputs that work on `main`.
- **Visibility.** The repo is public, so PR comments, the summary's hidden ledger and workflow logs are world-readable. `gh api repos/marcusk639/software-dev-team/collaborators` lists only `marcusk639` (admin). Anyone can react or reply to comments, so only Marcus's feedback can count.
- **Private channel.** Draft repository security advisories are available on public repos on any plan, so recovery-platform's channel applies as is.

## 8. Volume, size, and what already catches what

- **Volume.** Five PRs, all on 2026-10-26, by `marcusk639`. Sizes: #1 +416/−272 (30 files), #2 and #3 +4,838/−398 (51 files), #4 +4,153/−799 (41 files), #5 +1,974/−264 (26 files). Roughly half of each large PR is tests. The 90-day count is the whole history, so turn caps must be sized from PR size, not volume.
- **What is already checked:**
  - **No CI at all.** There are no workflows, no git hooks (`core.hooksPath` unset, no hooks installed) and no `CLAUDE.md`/`AGENTS.md`.
  - `pnpm typecheck` and `pnpm test` run locally only, by convention. Every PR body reports their results.
  - Marcus runs multi-agent local reviews before merging (PR #2: "A five-agent PR review…", PR #5: "five-agent review of PR #4 and four re-review rounds").
- **What the reviewer must not duplicate:** generic code review (already done locally, several times over), type errors and failing tests. The reviewer runs no code, and with no CI nothing on GitHub checks either. The reviewer's distinct edge is a fresh pass over the string links in §3, the loosening check (L15), and PR-text accuracy against the diff.
