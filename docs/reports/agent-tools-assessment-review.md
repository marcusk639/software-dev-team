# Review of the agent tools assessment

Reviewed: `docs/reports/agent-tools-assessment.md`, judged against `docs/prompts/agent-tools-assessment.md`, at commit `09f238e` with `@anthropic-ai/claude-agent-sdk` 0.3.283. SDK line citations are to `node_modules/@anthropic-ai/claude-agent-sdk/sdk.d.ts` (`sdk.d.ts`) and `sdk-tools.d.ts`. "Binary" means the bundled CLI at `node_modules/.pnpm/@anthropic-ai+claude-agent-sdk-darwin-arm64@0.3.283/.../claude` (CLI version string `2.1.283`), searched with `strings`. For every binary claim below I give the literal text to search for, so the owner can reproduce it with `strings <binary> | grep -F '<literal>'`. No paid API call was made.

## 1. Verdict

The report's code reading and probe results hold up. All of its `denyReason` observations reproduce, and almost every `sdk.d.ts` citation behind a P1 or P2 says what the report claims. The report goes wrong in one way that matters: it models `--yes` as "everything the hook doesn't deny runs". In the CLI's permission engine, `acceptEdits` auto-approves only file edits inside `--cwd` and seven filesystem commands (`mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed`). It routes writes outside `--cwd`, writes to config and secret paths, and every other Bash command to an "ask". With no `canUseTool` to answer it, an ask is refused. Two things follow. Most of the "observed bypasses" can't run unattended. More importantly, unattended runs probably can't run the project's tests at all, so qa-tester's core job fails under `--yes`, and nothing in the report's P1 list addresses that. Four of the report's P1 items survive, but #1 and #4 need changes before they're built. The owner should run one cheap experiment (E1 in section 5) before committing to the list, because it confirms or refutes the `--yes` finding that reorders it.

## 3. Decision-changing problems

### D1. `--yes` does not auto-approve "every tool call". This changes #2's threat model and exposes an unlisted P1 gap.

- **Report's claims.** Section 3, step 8: "Under `--yes`, `acceptEdits` approves it without asking." Section 4 (database-specialist): "under `--yes` nothing pauses, and the destructive commands it should stop for… aren't denied". #2: "The usage text promises 'destructive commands stay blocked' under `--yes`… The probes show common equivalents getting through."
- **Verdict: Wrong** as a description of runtime behavior. The probes themselves are **Confirmed**: they test `denyReason` alone, not what the CLI then does.
- **Evidence:**
  - Types: `acceptEdits` is "Auto-accept file edit operations" (`sdk.d.ts:1986`). An `ask` decision "asks the user to confirm (a headless session refuses instead)" (`sdk.d.ts:2731`). `--yes` passes `acceptEdits` and no `canUseTool` (`src/orchestrator/index.ts:50,54`), so there is no approval surface.
  - Binary, Bash under `acceptEdits`: `var xNo=["mkdir","touch","rm","rmdir","mv","cp","sed"]` and `if(n.mode==="acceptEdits"&&ANo(s))return{behavior:"allow"`. Any other base command returns "No mode-specific handling".
  - Binary, Write/Edit check (the function containing `if(r.mode==="acceptEdits"&&D)return{behavior:"allow"`): before mode approval it runs a sensitive-path check that returns `ask`. That check covers `.claude`, `.git`, `.husky`, `.vscode` and others (`var r6n=[".git",".vscode",".idea",".claude",".husky",…]`), plus files including `.mcp.json`, `.envrc`, `.npmrc` and shell rc files (`var NMt=[".gitconfig",…,".envrc",".ripgreprc",".mcp.json",".claude.json",".npmrc",…]`). `acceptEdits` approves only when the path is inside a working directory. Outside, it returns `ask`.
  - Binary, headless handling: asks are converted to denials with the reason `"no approval surface in this session; permission request denied automatically"` (constant `hKn`, applied by `function Bd(e)` in the print-mode permission path).
- **Corrected conclusion.**
  - Under `--yes`, these are refused before they run (after the hook passes them): `git checkout -- .`, `git restore`, `git branch -D`, `git push origin +main`, `prisma migrate reset`, `dropdb`, the download-and-run forms, `python -c`/`node -e`, writes outside `--cwd`, and writes to `.claude/`, `.mcp.json`, `.envrc` and `.npmrc`. In interactive mode they reach the operator's `allow? [y/N]` prompt with the command shown (`permissions.ts:152-158`).
  - What actually runs unattended is `rm -R build`, `rm --recursive --force build`, and `sed -i`/`mv`/`cp` over arbitrary in-tree files (auto-approved), along with Read, Grep and `cat` of `.env`. That makes #2's `rm` fix the urgent part.
  - The same mechanism refuses `pnpm test`, `tsc`, `git commit` and every other verification command under `--yes`, unless the target repo's own `.claude/settings.json` allows them. The commit message's test target declared `allow:["Bash"]` (`orchestrator/index.ts:58-59`), which would hide this.
  - Under `--yes`, qa-tester's "Run the tests" (`qa-tester/prompt.md:10`) and the manager's "Require the evidence — the test output" (`orchestrator/prompt.md:16`) can't be met. #3 would mostly record refusals, and #5's "QA must have run a command" gate would loop.
  - **The fix is item 2 of the corrected list, and it must land with #2.** Once Bash is granted, the regex denylist becomes the only gate, so the bypasses the report observed become live.
- **Confidence.** The types and the binary agree, but no live run has confirmed it. It is the first experiment in section 5.

### D2. Delegation guard (#1) as specified blocks target-repo agents the code loads on purpose.

- **Report's claim.** #1: "A delegation to anything other than the ten roles in `ROLES`… is denied."
- **Verdict: Partly right.** The escape is real:
  - Built-in agents are offered next to programmatic ones. Binary: `function PEe(){let e=JZ();if(e==="none")return[];…let n=[Qq];…` with `var Qq={agentType:"general-purpose"`.
  - The binary contains the report's quoted string, `"…or omitting it — starts a fresh agent (general-purpose by default)."`.
  - `model` "takes precedence over the agent definition's model" (`sdk-tools.d.ts:763-766`).
  - My probe confirms that `denyReason` returns null for `Agent` with `general-purpose`, `fork`, `isolation:"remote"`, an omitted type, and `qa-tester` with `model:"haiku"`.

  The spec misses a conflict, though. `settingSources: ["project"]` is there "needed for its CLAUDE.md **and agents**" (`src/orchestrator/index.ts:55-56`), so a target repo's `.claude/agents/*.md` are deliberately available, and an allow-list of `ROLES` silently denies them.

- **Corrected conclusion.** Before building, the owner must choose:
  - (a) Deny target agents and update the comment.
  - (b) Allow target agents by name, accepting that one with no `tools` "inherits all tools from parent" (`sdk.d.ts:44`), which is a scoping escape the trust boundary already accepts.

  Either way, keep the `model` and `fork`/`remote` rules. As a second layer, the SDK reads an env var, `CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS`. It's listed in `sdk.mjs`'s env table, and the binary has `if(a.CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS&&Ae())return"none"`. It removes `general-purpose` and the other built-ins from the menu, so the manager isn't offered them at all. It isn't in `sdk.d.ts`, so treat it as undocumented. It doesn't cover `fork` or `model`, so the hook stays the enforcement. Matching both `Agent` and `Task` is harmless but no longer an open question (section 5).

### D3. The manager can already ask a question mid-run, but the gate breaks it (#4).

- **Report's claim.** Section 4, orchestrator gap (b): "It can ask a question but can't receive an answer: the run ends."
- **Verdict: Partly right.** True under `--yes`. In interactive mode the SDK provides a channel and the code mishandles it.
- **Evidence:**
  - `AskUserQuestionInput` is in the built-in tool union (`sdk-tools.d.ts:31`). Its `answers` are "User answers collected by the permission component" (`sdk-tools.d.ts:2648-2653`).
  - Binary: the tool's `checkPermissions` returns `{behavior:"ask",message:"Answer questions?"…}` and it declares `requiresUserInteraction(){return!0}`, so in interactive mode it reaches `canUseTool`.
  - `createPermissionGate` prints only `toolName` plus `command`, `file_path` or `pattern` (`src/permissions.ts:152-155`). For this tool that is just `⚠ AskUserQuestion`. A "y" returns `{ behavior: "allow" }` with no `updatedInput` (`:161-162`), so the questions are never shown and no answers come back.
  - Under `--yes`, the same ask is refused (D1), so `--resume` is still the only route there.
- **Corrected conclusion.** Item 5 of the corrected list: special-case `AskUserQuestion` in the gate (print the questions and options, read the choices, return `updatedInput` with `answers`), which is tens of lines; keep `--resume` for unattended runs. Also print the session id on error exits. `src/index.ts:149-152` returns before `:154-156`, so a run stopped by max-turns or budget, which is the case most worth resuming, prints no id. Whether the preset exposes `AskUserQuestion` in SDK sessions shows up in the `init` tool list (E1).

### D4. #2 claims to "stop secret reads" but leaves the process environment open.

- **Report's claim.** Summary table #2: "…and stop secret reads". Catalog #2 lists file reads only.
- **Verdict: Partly right.** File reads are covered. The API credential isn't.
- **Evidence:**
  - `runTeam` sets no `env`, so the CLI and its Bash inherit `process.env` (`sdk.d.ts:1641-1647`). That includes `ANTHROPIC_API_KEY` when set (`src/index.ts:125`).
  - My probe: `printenv ANTHROPIC_API_KEY`, `env` and `echo $ANTHROPIC_API_KEY` all return null from `denyReason`.
  - Binary: subprocess env scrubbing is on only when `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` is truthy or `GITHUB_ACTIONS` is set (`_e??=Yt(e)||Yt(process.env.GITHUB_ACTIONS)&&!No(e)`). Setting it also forces the permission mode to `default` (`"Permission mode forced to default — CLAUDE_CODE_SUBPROCESS_ENV_SCRUB is set"`), which conflicts with `--yes`.
- **Corrected conclusion.** A regex can't meaningfully close this. Dropping the key from `Options.env` would break the CLI's own authentication. The native control is the sandbox's `credentials.envVars` with `mode: "deny" | "mask"` (`sdk.d.ts:3509-3526`), which the report doesn't mention. Fold it into #6, and in the meantime say in #2 that env secrets remain readable. Severity is moderate. Exfiltration needs an outbound channel, and under `--yes` WebFetch to an arbitrary host takes the same ask path [Inferred from D1, not separately observed].

### D5. #2's containment rule, as specified, keys on the wrong directory and ignores symlinks.

- **Report's claim.** #2: "Write and Edit to a path that resolves outside the hook's `cwd` (`BaseHookInput.cwd`, `sdk.d.ts:174`) are denied."
- **Verdict: Unsupported.** `sdk.d.ts:174` declares only `cwd: string`. Nothing says it equals `--cwd`, and a worktree-isolated subagent (#13) or a `cd` in Bash can plausibly change it.
- **Evidence.** My probe: `ln -s ~ home` returns null, and so does Write to `home/.zshrc`. A lexical "inside cwd" check passes that path.
- **Corrected conclusion.** Close over `options.cwd` in `createSafetyHooks(cwd)`, and compare `realpath` of the nearest existing parent. The CLI already resolves symlinks for its own write check (the binary refuses with `"Refusing to write … it is a symbolic link"`). Because the CLI already asks for outside-cwd writes (D1), this rule matters mainly in interactive mode and once target allow-rules or item 2 grant more.

## 7. Minor issues

- Section 3, step 8, labels "hooks fire inside subagents" **[Inferred]**, but `sdk.d.ts:181` states it.
- #3: "Alternative with no hooks… That loses `agent_type`" is **Wrong**. The main-thread `Agent` tool_use block carries `subagent_type` (`sdk-tools.d.ts:762`), and subagent messages carry that block's id as `parent_tool_use_id` (`sdk.d.ts:3600`). A stream-built ledger keeps role attribution.
- #4: "Sessions are stored per project directory (`sdk.d.ts:1809`)" is **Unsupported**. The line says only `~/.claude/projects/`.
- #13: the claim that `PROTECTED_IN_COMMAND`'s `.git/` rule "may interfere" with merging is **Unsupported**. That rule applies only when `writesAFile` matches (`permissions.ts:82-90`), and `git merge` and `git worktree add` don't match it.
